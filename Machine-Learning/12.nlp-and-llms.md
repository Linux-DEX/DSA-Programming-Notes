# Natural Language Processing, Embeddings, and LLMs

Text was long treated as categorical columns you could count. Modern practice treats it as a dense, learned representation — and at the far end, as a task performer you instruct. This file follows that arc, from counting words to prompting a large language model.

## From text to numbers: the classical pipeline

A model consumes numbers. Every text system, classical or modern, starts with the same decisions:

1. **Tokenization.** Split text into units. Whole words (with `unknown` for rare ones), **subwords** such as byte-pair encoding, or characters. Subwords win today: nothing is ever “unknown,” and rare words are composed of pieces it has seen.
2. **Cleaning and normalization.** Case folding, punctuation, HTML stripping — applied with the same rules at training and prediction time, ideally inside the pipeline.
3. **Vectorization.** Turn each sequence of tokens into a fixed-size numeric input.

### Counting representations

- **Bag of words:** a count per vocabulary word. Order is discarded. “Not good” and “good, not” become the same row for many purposes — n-grams (pairs, triples) buy some of the order back at the cost of a larger vocabulary.
- **TF-IDF:** weight a word by how often it appears in a document, discounted by how often it appears everywhere else.

```text
tf-idf(w, document) = tf(w, document) · log(N / df(w))
```

A word that appears in every document gets a weight near zero. A word that is frequent in one document and rare overall ranks high. TF-IDF is a strong baseline for classical text classification and for keyword-style search, and it needs no training — worth checking against anything fancier.

- **One-hot and hashing** variants trade memory and exactness. Hashing avoids maintaining a vocabulary but accepts collisions.

The gap between documents and their representations is always the same warning from [1.fundamentals.md](./1.fundamentals.md): if the signal lives in word order or in what was *not* written, counting representations cannot carry it.

## Word embeddings

Counts are sparse and scattered. An **embedding** places each token at a point in a dense vector space, trained so that usage predicts position.

- **word2vec** trains a tiny probe (“predict a neighboring word”) and keeps the weights as the embedding. Words used in similar contexts land close together; analogies appear as vector arithmetic of varying reliability.
- **GloVe** factors a global co-occurrence matrix into the same kind of space.
- **fastText** embeds subword pieces and sums them, so a word never seen in training still gets a usable vector from its parts.

What embeddings buy: distances (cosine similarity especially) as a graded notion of relatedness, and downstream models that start with meaning instead of zero-covariance counts.

What they do not buy:

- One vector per word. “Bank” in “river bank” and “bank fee” is one point, because early embeddings had no context.
- Nothing about composition. The point for a phrase is an average of its words at best.
- The biases of the training corpus, often amplified on gender, ethnicity, and other associations. An embedding is a compressed census of what people wrote. Test for it (neighbor lists of profession words) when the downstream decision affects people.

## Contextual embeddings and pretrained encoders

Contextual models solve the one-point-per-word problem. A transformer encoder (see [11.deep-learning.md](./11.deep-learning.md)) builds the vector for each token *after* reading the whole sentence, so “bank” gets two different vectors in the two sentences above.

The standard recipe:

```text
pretrain a transformer by masking tokens (BERT-style)
→ the model’s layers encode rich context
→ fine-tune on your labeled task (sentiment, NER, similarity)
```

A classification head sits on top for tasks. For similarity and search, the hidden vector of a whole sentence (**sentence embedding**) is what you keep, and it is the address of a text inside a vector space. This is the workhorse of everything labeled “semantic” below.

Sentence embeddings power **semantic search**: embed every document, embed the query, return nearest neighbors. That works when nearness in the embedding means nearness in meaning you care about, which is an empirical claim — check recall on your own queries, not the vendor’s benchmark.

## Evaluating text models

| Task | Metrics |
| --- | --- |
| Classification / sentiment | Precision, recall, F1 as in [6.model-evaluation.md](./6.model-evaluation.md) |
| Named entity recognition | Precision/recall on entity *spans*, not on tokens |
| Retrieval / semantic search | Recall@k, MRR, NDCG at the k your product shows |
| Language-model quality | Perplexity (lower = better prediction of held-out text); task-level metrics when the model is evaluated as a system |

Perplexity is a training-side signal. A system that answers a question has to be judged on its answers, which is where evaluating LLMs gets harder — see below.

## Large language models

An LLM is a transformer trained as an autoregressive next-token predictor at enormous scale. That one objective, given enough data and capacity, induces capabilities no one programmed: writing, translation, code, question answering. Training happens in stages:

1. **Pretraining:** predict the next token on internet-scale text. The model learns language and a startling amount of world knowledge, but it follows no instructions yet — continuing what it saw is all it does.
2. **Supervised fine-tuning:** train on curated instruction–response pairs so the model learns the shape of “answer the question asked.”
3. **Preference tuning (RLHF, DPO):** collect human preferences between answers and tune the model toward preferred ones. Output style, helpfulness, and refusal behavior are shaped here.

LLM APIs and their open-weight relatives mostly expose stage 3 models, so the practitioner’s job is no longer modeling in the classical sense. It is harnessing, grounding, and evaluation.

### Prompting

The prompt is the program. Working principles:

- Give the task, the format of the answer, and any constraints, and show an example (**one-shot or few-shot**) for the exact format you want.
- **Chain of thought**: for multi-step reasoning tasks, asking for the intermediate steps (or examples that include them) usually improves accuracy — at the cost of more tokens. It is not magic; the model spends more computation before committing.
- Structure the answer (JSON fields) and **validate the parse**; treat malformed output as a retryable failure, not a silent null.
- Keep the context honest: paste the actual source text when the answer depends on a document, rather than trusting recall.

### Retrieval-augmented generation (RAG)

An LLM does not know your documents, your unimplemented policy, or what happened after its training cutoff. RAG supplies the facts at run time.

```text
query → embed → retrieve top-k chunks → assemble prompt
      (query + retrieved chunks + instructions)
      → LLM answers grounded in the chunks
```

Build sequence:

1. **Chunk** the corpus (paragraph-ish, with token overlap) so retrieved pieces are self-explanatory.
2. **Embed and index** chunks in a vector store. On the query, embed and run nearest-neighbor search (approximate methods such as HNSW trade a small recall cost for speed at scale).
3. **Assemble the prompt** with the question, the chunks, and an explicit instruction to use only those sources.
4. Optionally **rerank** retrieved chunks with a model that reads query and chunk together, since the easy nearest-neighbor pass is fast but blunt.

RAG versus fine-tuning is a decision chart, not a trend:

| | RAG | Fine-tuning |
| --- | --- | --- |
| Changing knowledge | Update the index — instant | Retrain — slow |
| Style/format learning | Weak (can show examples) | Strong |
| Traceable answers | Yes — cite the chunk | No |
| Failure mode | Poor retrieval → confident nonsense | Wrong style or stale facts baked in |

Practical default: RAG first for knowledge, fine-tuning only when behavior (format, tone, domain vocabulary) is the shortfall, and the two together when both are needed.

### Evaluation of LLM systems

- **Retrieval first.** If the correct chunk is not in the top-k, no amount of generation fixes the answer. Measure Recall@k on a labeled query set.
- **Groundedness and faithfulness:** does the answer state what the retrieved chunk supports? Checkable against the source, automatically for many question types.
- **Quality sets and judges.** For open-ended answers, rubric-based scoring by another LLM (“LLM-as-judge”) is standard. It is cheap and directional — but the judge has its own biases (verbosity, confidence, formatting). Human-calibrate the judge on a sample, and never use a judge trained this way to certify itself.
- **Regression testing in the prompt lifecycle.** Every prompt change is a code change. Keep a fixed test set of inputs with expected behavior, run it on every change, and record scores the same way CI records tests (see [10.deployment-and-mlops.md](./10.deployment-and-mlops.md)).

### Failure modes to respect

- **Hallucination.** Fluent, confident, invented. Grounding (retrieval), verification against sources, and calibrated prompts (“say you do not know”) reduce it; they do not eliminate it. Never wire an ungrounded generation to an irreversible action.
- **Prompt injection.** The instruction to ignore instructions can arrive inside your retrieved content. Treat retrieved text as data, not as commands.
- **Leaks.** Sensitive data sent to a hosted API is data you sent. Know the retention policy of the endpoint and redact what the job does not need.
- **Cost and latency.** Tokens are billed; long contexts and retries add up. Log token counts the way you would log query times.
- **Non-determinism and model upgrades.** The same prompt can return different text, and an upgraded model shifts behavior for every prompt at once. Pin versions in production and re-run the test set on any change.

## Where all of this sits with the earlier notes

Everything upstream still applies: define the decision, keep a held-out evaluation that matches deployment ([4](./4.data-preparation-and-eda.md), [6](./6.model-evaluation.md)), and ship with logging and monitoring ([10](./10.deployment-and-mlops.md)). What changes is that a **dataset for improvement now comes from production logs** of query, retrieved chunks, and accepted answer — the same loop the classical notes describe, with text instead of rows.

A final sanity check that keeps the memory of an older lesson: before attaching an LLM to any task, ask what a trained classifier or a search index would do on the same inputs. On many production workloads, an embedding model plus a reranker — or even TF-IDF — gets 90% of the value at 1% of the cost, and the LLM belongs only to the slice that genuinely needs generation or synthesis.
